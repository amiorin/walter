Walter

Walter provisions a cloud VM (OCI, Hetzner Cloud, DigitalOcean — or an existing host), then configures it into a fully-loaded, personalized development environment — Doom Emacs, Devbox, asdf, Tailscale, Docker, Caddy, Redis, and a constellation of dotfiles — with a single command.

Clojure / Babashka Green OpenTofu Ansible Ubuntu 24.04 LTS OCI · Hetzner · DigitalOcean MIT

Overview

Walter is a thin orchestration layer over OpenTofu and Ansible written in Clojure. It exists for one purpose: turn the empty cloud account you just opened into a productive Linux workstation in minutes. The workflow is:

  1. Render OpenTofu templates and provision a VM.
  2. Render Ansible playbooks against the new VM’s public IP.
  3. Run a root-level role (system packages, users, Nix, Docker) and a per-user role (Devbox, asdf, dotfiles, Doom Emacs).
  4. Update local SSH config so the host is reachable by name.

The stages are composed as a Green DAG. You run the whole thing with ./green create; --start and --end run a slice of the graph when you are debugging one stage.

Everything Walter builds — users, repositories, packages, the tailnet — is desired state in green.edn, not source. The compute stage and the local SSH stage are shared with once; Walter owns only the remote Ansible run.

Why Clojure?

Workflows are data: each step is a vector of keyword + args. Clojure’s data-first style fits the pipeline.

Why Babashka?

Sub-second start-up. The bb run CLI feels like make targets but composes like Clojure functions.

Why OpenTofu?

Open-source Terraform fork; identical CLI, no license drama. Same providers (hcloud, oci).

Why Ansible?

Idempotent, agentless, ubiquitous on Ubuntu. Roles are plain YAML; no compiler dance.

Quick start

Assuming Babashka, OpenTofu and Ansible are already on your PATH (see Prerequisites):

# 1. Clone and enter the repo
git clone https://github.com/bigconfig-ai/walter
cd walter

# 2. Describe the workstation you want
$EDITOR green.edn

# 3. Drop your credentials into .envrc.private (see .envrc.private.example)
cp .envrc.private.example .envrc.private
$EDITOR .envrc.private

# 4. Authenticate against the hyperscaler
#    OCI: oci setup config             (writes ~/.oci/config, profile DEFAULT)
#    Hetzner: export GREEN_PAR_HCLOUD_TOKEN=...

# 5. Look before you leap
./green build                # render only — no tofu, no ansible, no credentials
./green create --dry-run     # print the DAG actions, touch nothing

# 6. Provision and configure end-to-end
./green create

That last command takes about 10–20 minutes on a fresh box. When it returns, the VM is reachable over Tailscale and Doom Emacs is compiled.

Note Inside this repository run the launcher through Babashka — bb green build — so bb.edn’s local roots for green and once apply. A standalone copy of ./green resolves them as pinned git dependencies instead.
Safe by construction build and create --dry-run read no GREEN_PAR_* at all. A clean dry-run therefore says nothing about whether your credentials work — it only proves the desired state renders.

Environment variables

Walter reads its configuration from exactly two sources, in order of override:

  1. Desired state — green.edn, or whatever -f|--file names
  2. Environment variables — GREEN_PAR_*, overlaid onto matching flat keys before anything runs

A variable name is the key uppercased with hyphens as underscores, so :hcloud-token is supplied by GREEN_PAR_HCLOUD_TOKEN. There is no TF_VAR_* alias and no second mechanism. Overrides are coerced to the type of the value they replace, so GREEN_PAR_COMPUTE_PREVENT_DESTROY=false stays a boolean rather than the truthy string "false".

Credentials never appear in green.edn. They live in .envrc.private (untracked):

# .envrc.private.example
export GREEN_PAR_HCLOUD_TOKEN=...                                # Hetzner Cloud API token
export GREEN_PAR_DO_TOKEN=...                                    # DigitalOcean API token
export GREEN_PAR_R2_ACCESS_KEY_ID=...                            # R2 state backend
export GREEN_PAR_R2_SECRET_ACCESS_KEY=...
export ATUIN_LOGIN="atuin login -u me -p ... -k '...'"       # looked up at play time

OCI needs no GREEN_PAR_* — it authenticates through the profile named in ~/.oci/config — and S3 uses OpenTofu’s ambient AWS credential chain. ATUIN_LOGIN is not a Walter variable at all: the user role emits a lookup('ansible.builtin.env', 'ATUIN_LOGIN') expression, resolved when the play runs rather than when the file is rendered, so the value never lands in the work directory.

Any flat key can be overridden the same way, not just credentials:

GREEN_PAR_PROFILE=laptop ./green build
GREEN_PAR_PROVIDER_COMPUTE=no-infra GREEN_PAR_NO_INFRA_COMPUTE_IP=203.0.113.10 ./green build

Keys nested under :walter are the exception — edit the file, or keep a second desired-state file and select it with -f.

Hetzner parameters

The Hetzner template is simpler — it expects GREEN_PAR_HCLOUD_TOKEN and the SSH key alias already registered in your Hetzner project:

;; green.edn
:provider-compute "hcloud"
:hcloud-name "walter"
:hcloud-image "ubuntu-24.04"
:hcloud-server-type "cx23"
:hcloud-location "hel1"
:hcloud-ssh-keys "name-or-id-already-in-the-account"

To switch hyperscaler, change :provider-compute — or set GREEN_PAR_PROVIDER_COMPUTE=hcloud for one run. The OpenTofu template tree is selected by that key alone; providers are separate directories, not conditionals in one file.

No infrastructure Set :provider-compute "no-infra" to configure a machine that already exists — a laptop, a bare-metal box, a VM someone else provisioned. OpenTofu creates nothing and the host details come from :no-infra-compute-ip, -user, -sudoer and -uid.

green commands

Four commands, all reading ./green.edn unless -f|--file names another file:

./green build      # render <workdir>/<profile>/ only — no tofu, no ansible
./green create     # provision and configure
./green delete     # destroy the compute stage
./green describe   # providers, compute status, workstation summary
FlagEffect
-f, --fileSelect a desired-state file. One project can hold several workstations: ./green build -f laptop.edn.
--dry-runStamp :green/dry-run. Every side-effecting step prints what it would do and is skipped.
--start, --endRun a slice of the graph — --start :walter/ansible-remote reruns just the workstation play.
Deleting is guarded :compute-prevent-destroy defaults to true, which renders lifecycle { prevent_destroy = true } on the compute resource. A real delete refuses to start until you authorize it in the environment: GREEN_PAR_COMPUTE_PREVENT_DESTROY=false ./green delete. Authorize it that way rather than by editing committed desired state.
Rerunning is safe create is idempotent — every Ansible task is guarded by a creates: check. After a partial failure, rerun create; never reach for delete to fix it, or you will destroy the box holding your repositories and shell history.

Credentials (GREEN_PAR_*)

Which variables a run needs depends entirely on the two providers you selected:

SelectionRequired
:provider-compute "oci"none — the profile in ~/.oci/config
:provider-compute "hcloud"GREEN_PAR_HCLOUD_TOKEN
:provider-compute "digitalocean"GREEN_PAR_DO_TOKEN
:provider-compute "no-infra"none
:provider-backend "s3"none — OpenTofu’s ambient AWS chain
:provider-backend "r2"GREEN_PAR_R2_ACCESS_KEY_ID, GREEN_PAR_R2_SECRET_ACCESS_KEY
:provider-backend "local"none

A missing one is caught before any provider is contacted: create and delete validate the environment in their first step and fail with the variable’s name.

No credential reaches a rendered file. OpenTofu receives each one through the process environment under the variable that provider reads natively (:hcloud-token → HCLOUD_TOKEN), and R2 authenticates through AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY rather than through backend.tf.json — naming them there would also copy them into .terraform/terraform.tfstate.

The DAG

wire-fn in walter.workflow returns [step-fn & next-steps] for each step and switches on :green/event. Create and build:

start ─ tofu-compute ─┬─ ansible-local
                      └─ ansible-remote

Delete runs it backwards, undoing the Ansible stages before the machine they configured disappears:

start ─ ansible-cleanup ─ tofu-compute
1
tofu-compute
provision VM
2
ansible-remote
build workstation
2
ansible-local
~/.ssh/config

The two Ansible stages are independent, so the engine runs them concurrently — they share step number 2 above. Walter has a single Tofu stage and therefore no join, which is the main way its graph is simpler than Once’s.

The workflow also attaches three kinds of advice:

  • backend advice :before the Tofu step, which writes backend.tf.json for the selected state backend,
  • progress/advise, which prints the >>> / <<< lines with per-step timings,
  • dry-run/advise over the side-effecting steps, which is what makes --dry-run touch nothing.

How the Ansible stages discover the new VM’s IP without you typing it: tofu-compute parses the stage’s params output into :once/compute-params and merges ip, user, sudoer and uid into the top level of the opts map that flows downstream. For build and --dry-run a fallback map stands in, so rendering never needs live state — or credentials.

Delete cannot re-derive those values, because the stage that produced them is about to be destroyed. adopt-existing-state reads the already-applied outputs back out of OpenTofu state before teardown starts.

Namespaces

Five, plus a launcher that holds none of them. Adding a sixth needs a genuinely new concern.

FileResponsibility
green-walter/greenThe launcher, and the skill payload. Resolves the three libraries, checks the contract, finds the desired-state file, dispatches. No logic of its own.
walter.workflowThe DAG: start-step, wire-fn, the cleanup step, and the backend advice.
walter.validateThe provider registry — Once’s, narrowed to Walter’s two slots — and the desired-state and credential checks it drives.
walter.toolsThe ansible-remote stage: template specs, the pure generators for inventory.json, default.config.yml, packages.yml, repos.yml and ssh-config.yml, and the wrappers around Once’s two stages.
walter.describeThe post-provisioning report: providers, compute classification, workstation summary.
walter.utilsThe contract number.
Why the launcher is empty Everything it used to hold — validation, the graph, backends, pin — is now in the library, where the test suite reaches it. A single Babashka script copied into a stranger’s project is the one place none of that can be tested, so the only code left there is the part that cannot live anywhere else: resolving the library in the first place.
Convention Steps take opts and return opts, reporting failure through :green/exit and :green/err rather than by throwing. Pure builders stay pure: data-fn, inventory, packages, repos and ssh-config take data and return data, so the tests drive them without spawning a process.
Reuse over reimplementation The compute stage, the local SSH stage, the small YAML emitter and the process helpers all come from once. Walter depends on it rather than copying it, because two copies drift.

The Green engine

Walter doesn’t reinvent orchestration; it leans on green, a DAG workflow engine. The engine provides:

  • green.workflow — a graph of steps threaded by an opts map, with parallel branches, joins, and advice (before/after/around) attached per step.
  • green.scaffold — the flat file-spec DSL: one spec per file, rendered with Selmer on create and used to name the targets to remove on delete.
  • green.tofu / green.ansible — event-aware steps that render, then run tofu or ansible-playbook, with backend and inventory advice.
  • green.cli — reads the desired-state file, overlays GREEN_PAR_*, stamps :green/event, runs the workflow.
  • green.progress / green.dry-run — the >>> / <<< trace lines and the --dry-run skip.
  • green.yaml / green.process — the small YAML emitter the generated Ansible files use, and shelling out with a timeout that kills the process tree.

One map is threaded through every step. Reserved keys are namespaced; desired-state keys are plain kebab-case keywords.

KeyMeaning
:green/exit0 success, >0 failure — how steps report, instead of throwing
:green/err, :green/tracefailure message and stack trace
:green/event:build, :create, or :delete, stamped by green.cli
:green/dry-runset by --dry-run
:once/compute-paramsthe compute stage’s outputs, also merged to the top level
:green.scaffold/written, :green.scaffold/deletedpaths a scaffold touched

The companion package once ships the reusable compute and ansible-local stages. Walter owns only the remote Ansible stage, because that is the only part where a workstation differs from a single-server ONCE install.

Template rendering

Templates live under src/resources/io/github/bigconfig-ai/walter/tools/ansible/. green.scaffold maps a qualified keyword to a classpath resource and renders it with Selmer — one spec per file. There is no directory-tree copy, so every file is named explicitly.

Walter’s Ansible tree carries no Selmer variables at all: everything that varies is generated instead. So the twelve static files are copied verbatim through the one-line raw template:

;; src/resources/io/github/bigconfig-ai/walter/raw
<{ content|safe }>

Five files are generated from desired state — inventory.json and default.config.yml at the tree root, and packages.yml, repos.yml, ssh-config.yml under roles/users/tasks/, where the static main.yml pulls them in with import_tasks.

Why verbatim, not templated Green renders Ansible files with <{ }> and <% %> delimiters precisely so Jinja2’s {{ }} and {% %} survive untouched — and the role tasks rely on that. But roles/users/files/xterm-ghostty is terminfo source containing %<%t and \E[<%i, which Selmer would try to parse as tags. Copying the static files rather than rendering them sidesteps the collision entirely.

For the OpenTofu side, once does the equivalent, picking the subtree tofu/<provider-compute>/ based on the configured key. backend.tf.json is the exception to all of this — green.tofu writes it directly from the backend advice, outside the scaffold.

Profiles & the work dir

Each stage owns an isolated directory, <workdir>/<profile>/<tool> — the same layout Once uses, so both packages’ stages sit side by side without colliding. A build of the reference green.edn produces exactly:

.green/walter/
├── tofu-compute/     backend.tf.json  main.tf
├── ansible-local/    ansible.cfg  inventory.ini  main.yml
└── ansible-remote/   ansible.cfg  main.yml  inventory.json  default.config.yml
                      roles/root/{files,handlers,tasks}
                      roles/users/{files,tasks}

:profile does quadruple duty: it names the work directory, prefixes the remote state keys (<profile>/<tool>.tfstate), becomes the name the compute stage reports, and is the Host alias written into your local ~/.ssh/config. Change it — or override it for one run with GREEN_PAR_PROFILE — and you get a second, fully isolated workstation.

Note .green/ is generated output, and is ignored by Git. Never hand-edit files there; your changes will be clobbered on the next render.

System role (root, become: true)

The Ansible playbook (main.yml) runs two roles. The system role does the privileged work:

  • Add a sudoers file for each managed user (NOPASSWD:ALL).
  • Install Determinate Nix via the official installer.
  • Trust managed users in /etc/nix/nix.custom.conf and restart nix-daemon.
  • Copy four shell hooks into /etc/profile.d/:
    • Z50-devbox.sh — sources devbox global shellenv into every shell.
    • direnv.sh — hooks direnv into bash.
    • ssh-agent.sh — symlinks $SSH_AUTH_SOCK to a stable per-user path (so zellij sessions don’t lose agent forwarding).
    • zellij.sh — alias ze for zellij attach --create $(whoami)@$(hostname).
  • Install Docker via the official get.docker.com script (retries 10× with 10s backoff).
  • Create each user named in :walter :users with their uid, home dir, and the docker group.
  • Drop :compute-pubkey into every managed user’s ~/.ssh/authorized_keys.
  • Install asdf v0.18.0 binary to /usr/local/bin.
  • Add Tailscale apt repo and install tailscale, fish, build-essential.
  • Install Caddy via its stable Debian repo.
  • Install Redis via the official Redis repo.

User role (ubuntu)

  • Install Ghostty terminfo (tic -x).
  • Install devenv and Devbox via nix profile add.
  • Provision the full devbox package set (one task per package, idempotent via creates:).
  • Refresh the devbox shell environment.
  • Provision asdf languages and tools.
  • Clone the configured repos into ~/code/personal/<repo>/main, plus any worktrees.
  • Install dotfiles by running bb install -p ubuntu inside dotfiles-v3/main.
  • If ATUIN_LOGIN is set, log in to Atuin and run atuin sync.
  • Clone Doom Emacs pinned at the user’s :doomemacs commit, run doom sync, pre-compile vterm, and install all the LSP servers Doom expects (Dockerfile, basedpyright, typescript, yaml, astro, mdx).
  • Generate ~/.ssh/config blocks pointing at the host’s <ip>.<tailnet> Tailscale hostname, where :walter :tailnet supplies the domain.

Customization

All personalisation happens in one file: green.edn. Nothing about the workstation is hardcoded in the Clojure source, so customising Walter never means editing a namespace. Change the file and rerun ./green create, which is idempotent.

;; green.edn — the workstation
:walter {:tailnet "example-tailnet.ts.net"
         :users [{:name "ubuntu" :doomemacs "<commit-sha>" :remove false}]
         :repos [{:user "ubuntu" :org "acme" :repo "site"
                  :branch "main" :worktrees []}]
         :packages [["ripgrep" "rg"]
                    ["fish" "fish"]]}

Add a package

Append a [package cli] pair to :packages:

["helix" "hx"]   ; devbox installs "helix"; the guard looks for "hx" on PATH

When the binary name matches the package name, repeat it — ["fish" "fish"]. Getting the second element wrong is harmless but makes the task rerun on every play.

Add a repo

{:user "ubuntu" :org "acme" :repo "my-new-repo"
 :branch "main" :worktrees ["feature-branch-wt"]}

Switch to Hetzner

  1. Set :provider-compute "hcloud" and fill in the :hcloud-* keys.
  2. Export GREEN_PAR_HCLOUD_TOKEN (put it in .envrc.private).
  3. Register your SSH public key in the Hetzner project and name it in :hcloud-ssh-keys.
  4. ./green build to check the render, then ./green create.

To try it for one run without editing the file: GREEN_PAR_PROVIDER_COMPUTE=hcloud ./green build.

Resize the OCI VM

OCI Ampere A1 Flex shapes are billed per OCPU+RAM-hour. To go larger:

:oci-ocpus 4
:oci-memory-in-gbs 24
:oci-boot-volume-size-in-gbs 200

Then ./green create --dry-run to preview and ./green create to commit. OpenTofu can resize Flex shapes in place — no destroy needed, which matters because delete would take your home directory with it.

Pin a new Doom Emacs commit

The pin lives on the user, so different users can run different Doom versions:

:users [{:name "ubuntu"
         :doomemacs "dd72eac1971616a6ebe81067cca33b14c148cbcd"   ; ← bump this
         :remove false}]

The user role’s Install doomemacs task reads {{ (users | selectattr(...))first.doomemacs }} with a hard-coded fallback commit.

Set an explicit uid

A user that names no :uid inherits the uid the image’s default user already has, reported by the compute stage — which is what you want on OCI, where ubuntu exists with uid 1001. The play creates accounts by uid, so add an explicit :uid only when you mean to override that, and only to a value no existing account holds.

Remove a user

Set :remove true on the entry — the system role’s Force removal task picks them up and the home directory is wiped. Deleting the entry outright does nothing; the account simply stops being managed. Drop the entry on a later run, once the removal has been applied.

Troubleshooting

OpenTofu can’t authenticate to OCI

Check ~/.oci/config exists and has a [DEFAULT] profile (matches :oci-config-file-profile). Test with oci os ns get. If you use the OCI CLI Docker image, you’ll need to bind-mount the config in.

S3 backend errors

Set your own :s3-bucket and :s3-region in green.edn, and make sure your local AWS credentials can write there. The S3 backend uses OpenTofu’s ambient credential chain, so there is no GREEN_PAR_* to set — if aws sts get-caller-identity works, so will the backend.

Ansible can’t SSH to the new VM

The OpenTofu template includes a remote-exec provisioner running ls — its job is to block until the SSH port is up. If that step succeeded but Ansible still times out, suspect: (a) wrong sudoer user (OCI is ubuntu, Hetzner Cloud is root); (b) the public IP changed between the stages. Run ./green describe, which reads the compute outputs and probes SSH, to see which.

describe says compute is absent

The compute stage holds no outputs, so it was never applied — usually because you ran build rather than create. Under no-infra compute is never absent, since OpenTofu creates nothing there; you will see unreachable instead, meaning either no host is configured or SSH failed.

Doom Emacs install hangs / fails

The Install doomemacs task does everything inline: clone, sync, compile vterm, install many npm-based LSP servers. If npm is wedged the task fails late. Re-running the playbook is safe — it’s gated by creates: ~/.emacs.d, so you’ll need to delete ~/.emacs.d on the VM to retry from scratch.

SSH agent forwarding is gone after reconnect

The /etc/profile.d/ssh-agent.sh hook stabilises the socket path. As of commit ecd905a the hook also guards against creating a circular symlink (older versions could re-link the file to itself on a second login).

Where did the rendered files go?

<workdir>/<profile>/<tool>/ — by default .green/walter/{tofu-compute,ansible-local,ansible-remote}/. Run ./green build to render them without touching a provider.

The launcher says the contract is too low

A standalone copy of green refuses to run against a walter older than it expects, rather than silently rendering from stale templates. If you are a user of the skill, re-copy green from an updated skill — the launcher has no pin command, because pinning reads the HEAD of whatever repository surrounds it and would stamp your project’s SHA. If you are working in this repository, run bb pin after committing and pushing.

Formatting

clojure-lsp clean-ns then clojure-lsp format. Both need clojure-lsp on your PATH; install via brew install clojure-lsp/brew/clojure-lsp-native.

REPL workflow

Steps are plain functions of opts, so the REPL needs no special harness — build an opts map and call one.

clojure -A:dev
(require '[clojure.edn :as edn]
         '[io.github.bigconfig-ai.walter.tools :as tools])

;; the desired state, plus what the compute stage would have reported
(def opts (merge (edn/read-string (slurp "green.edn"))
                 {:green/event :build
                  :ip "203.0.113.10" :user "ubuntu" :sudoer "root" :uid "1001"}))

;; the shape everything else is generated from
(tools/data-fn opts nil)

;; the generated files, as strings — no processes, no VM
(println (tools/inventory (tools/data-fn opts nil)))
(println (tools/packages  (tools/data-fn opts nil)))
(println (tools/repos     (tools/data-fn opts nil)))

;; render the whole stage into .green/
(tools/ansible-remote-step opts)

Because the generators are pure, this is the fast loop for a template or data change: no VM, no credentials, no waiting. The same holds for the report — describe/describe-report takes an injected runner in its multi-argument arities, so you can feed it canned command results.

The launcher itself is loadable too, which is how you exercise the DAG:

bb green build --start :walter/ansible-remote   # run one slice of the graph
